# 版本与分支规则

> 单人维护的小项目，规则要足够少才能坚持。这里是本项目实际采用的做法。

## 1. 三个概念先分清

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| `main` 分支 | **发布线**：永远指向"最新一个验证过的状态" | 不是"最老的分支"。让它停在旧版本，等于 GitHub 首页展示旧代码、用户 clone 到旧版 |
| commit | 一次完整改动的快照（不可变） | 不是"保存草稿" |
| tag（如 `v1.4.0`） | 给某个 commit 起的固定名字，**回档锚点** | 不是分支，不能在上面继续开发 |

**回档靠什么**：`git revert <commit>`（安全，生成反向提交）或 `git checkout v1.4.0`（只看不写）。
历史本身就是回档能力，不需要额外准备一个"旧分支"。

> 如果 `main` 一直停在旧版本，你会同时遇到三个问题：
> ① 仓库首页/README/截图都是旧的；② 每次合并都要解冲突；③ Release 和 main 对不上。
> 所以"main 保持最老"不是备份策略，是维护负担。

## 2. 两种工作流，按改动大小选

### A. 日常改动 → 直接在 main 上做（默认，90% 的情况）

适合：半天内能改完、能立刻编译 + 跑自检的改动。

```
git pull                                  # 开工前先拉
# 改代码…
build.ps1 -Strict                          # 编译零警告
tests\run-tests.ps1                        # ALL PASS
git add -A
git commit -m "fix(k02bs): 一句话说清改了什么、为什么"
git push
```

要点：**一次提交只做一件事**。改 K02BS 判定就别顺手调 UI 间距，否则回档时只能整块回退。

### B. 大改动 → 开短分支，验证完再合（10% 的情况）

什么时候值得开分支：

- 改动跨多个文件、要真机验证好几天，中途可能要推翻重来
- 要动协议/判定逻辑这类"改错了会误报"的地方
- 准备发版，但还没验证完，main 必须保持可用

```
git checkout -b feat/ladder-history        # 从 main 拉分支
# 改代码、提交（可以提交很多次，乱一点没关系）
git push -u origin feat/ladder-history     # 可选：推到远端备份
# 验证通过后合回 main
git checkout main
git pull
git merge --no-ff feat/ladder-history      # --no-ff 保留分支痕迹，方便日后看"这是一整块改动"
git push
git branch -d feat/ladder-history          # 本地删掉
git push origin --delete feat/ladder-history  # 远端也删掉
```

分支**寿命以天计，不以周计**。合并完就删，别留一堆僵尸分支。

## 3. 发版流程（每次发布都做）

1. 改 `src/AssemblyInfo.cs` 的版本号（或 `build.ps1 -Version 1.4.1`）
2. 在 `CHANGELOG.md` 顶部加一节
3. 提交：`git commit -m "chore: 版本 1.4.1"`
4. 打标签并推送：

```
git tag -a v1.4.1 -m "1.4.1：一句话摘要"
git push
git push origin v1.4.1
```

5. `tools\pack.ps1` 打包 → GitHub Release 上传 zip（见 `docs/04-发布到GitHub.md`）

版本语义：修 bug 升末位（1.4.1），加功能升中间位（1.5.0），改协议/不兼容升首位（2.0.0）。

## 4. 回档手册

| 想做什么 | 命令 | 注意 |
|---|---|---|
| 撤销某次提交（保留历史） | `git revert <commit>` 然后 `git push` | **首选**，安全，可再撤销 |
| 临时切到旧版本看代码 | `git checkout v1.4.0` | 看完 `git checkout main` 回去；别在这上面改 |
| 对比某版本与现在 | `git diff v1.4.0..main -- src/` | 只看某个目录就加路径 |
| 找回被删的文件 | `git log --oneline -- 文件路径` → `git checkout <sha> -- 文件路径` | |
| 老版本用户报 bug（hotfix） | `git checkout -b hotfix/v1.4.1 v1.4.0` → 修 → 合回 main → 打新 tag | 唯一必须开分支的场景 |

**不要**用 `git reset --hard` + `push --force` 改已经公开的历史——别人已经 clone 的仓库会错乱。

## 5. 提交信息怎么写

```
<类型>(<范围>): <做了什么>

<为什么这么做 / 影响范围>
```

类型：`feat` 新功能 / `fix` 修 bug / `refactor` 不改行为的重构 / `docs` 文档 / `chore` 杂务 / `test` 测试。

例：

```
fix(k02bs): 蓝牙连接证据改走 API，排除断开后残留的 HFP 电量属性

耳机已关机但 Windows 仍保留 HFP 电量 80%，上一版把它当连接证据 → 仍判双模。
```

半年后回来看 `git log`，这行字比代码有用。

## 6. 一句话版本

- **平时**：在 `main` 上小步提交，一次一件事。
- **大改**：开短分支，验完 `--no-ff` 合回来，删掉。
- **回档**：用 `revert`，用 `tag`，别让 `main` 停在旧版本。
