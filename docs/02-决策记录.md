# 决策记录（ADR）

记录「为什么这么做」。代码能说明做了什么，说明不了为什么——这份文件是接手时最该先读的东西。
新增决策请追加，不要改写历史条目；被推翻的条目保留原文并标注「已废止（见 Dxx）」。

---

## D1 设备识别只用型号级特征

**决策**：识别与匹配只允许 `VID/PID`、接口类型、音频端点 formfactor、设备类别。
禁止实例路径、USB 端口号、Container ID、序列号、音频端点 ID。

**理由**：这些值换台电脑、换个 USB 口、换同型号的另一只设备就会变，一旦写进配置键，
缓存和勾选状态全部失效。代价是**同型号多设备只能共用一张卡**——接受这个代价。

**落地**：`ConfigStore.IsSafeDeviceId()` 在写盘层拒绝含 `\ / # { }`、`VID_`、`PID_`、`MI_` 的键。
这是道硬闸：就算业务层写错，也落不进配置文件。

---

## D2 型号级键，而不是个体级键

**决策**：`MCHOSE`、`K02BS`、`046D:C539`、`BT:<名称>` 这类键作为配置主键。

**理由**：见 D1。补充一点：蓝牙键用设备名而不是 `BTHENUM` 实例 ID，
因为设备名在同型号不同电脑上一致，而实例 ID 每次配对都会变。

**副作用**：同型号两台共用勾选、阶梯参数和自定义名。文档已声明。

---

## D3 超时不写负缓存

**决策**：探测超时只累计失败次数并保留快速重试；只有设备「明确回答没有该特性」才写负缓存，
且要连续 2 轮才写。

**理由**：设备休眠时正常应答率很低。把「没说话」当成「不支持」，会让一只休眠的鼠标
在醒来后的 30 分钟里都读不到电量——这正是早期版本用户抱怨的问题。
冷启动那几秒接收器会应答但特性表未就绪，所以还要「连续 2 轮」才作数。

---

## D4 成功缓存按固件指纹失效

**决策**：缓存有效期很长（事实上的永久），但 `bcdDevice` 变化立即失效。

**理由**：刷固件后协议可能变；用指纹失效比用时间过期更准确。
指纹取**所有接口里最大的 bcdDevice**，因为接口枚举顺序在不同次启动间并不稳定。

---

## D5 断连不是立刻翻脸：10.5 秒重试 + 90 秒确认

**决策**：物理链路读不到时先记「漏拍」，10.5 秒后自动重试；
连续 2 次漏拍且距首次断开 ≥90 秒才正式判「未连接」，期间卡片显示「连接波动」并沿用最后电量。

**理由**：60 秒刷新间隔下，单次偶发失败不该让卡片翻成未连接；设备从休眠唤醒也有延迟。
**注意**：早期文档写的是「10 秒冗余」，那是重试间隔，不是确认时限——v1.4 文档已纠正。

---

## D6 计划任务直调 exe，不走 .cmd

**决策**：计划任务的 `<Command>` 是 `WirelessBattery.exe`，参数 `--tray`。

**理由**：走 `cmd / start` 会让令牌降级（任务本身是 HighestAvailable，经 cmd 启动后
子进程可能退回 Medium），而托盘注册需要与 Explorer 同级。任务不经资源管理器，
因此也不会触发 SmartScreen。`.cmd` 只用于「用户手动双击」这条路径。

**代价**：README 曾写「计划任务调用同一个 .cmd」，与实现不符，v1.4 已改。

---

## D7 托盘需要管理员权限是权限倒挂，用 UAC 自愈

**决策**：启动时先做 `Shell_NotifyIcon` 探针；只有「探针失败 + Explorer 是 High + 自己不是管理员 +
有 LinkedToken」四条同时成立，才 `runas` 重启自己（带 `--elevated` 防循环）。

**理由**：普通 Explorer 下绝不能弹 UAC，否则每次开机都打扰用户。
取消 UAC 后要重新抢锁继续跑，不能把用户关在门外。

---

## D8 运行时状态合并写

**决策**：最后电量、连接状态、双模快照等每轮都可能变的字段只在内存改（`SaveDeferred`），
由 20 秒定时器和退出时 `Flush()` 合并成一次整文件写；用户改设置仍立即写。

**理由**：一次刷新曾触发 2~3 次 155 行整文件重写（每天上千次）。
代价是极端情况下（进程被强杀）最多丢 20 秒的运行时状态——都是可重建的显示数据，不影响配置。

**不合并的例外**：阶梯计时锚点（`EstimateBt` 跳档）仍然立即写，否则「已保持」小时数会算错。

---

## D9 不按进程名杀进程

**决策**：v1.4 删除了 `KillOldInstances()`。多开由命名互斥挡住，不靠强杀。

**理由**：按进程名前缀杀进程会误伤用户另存的调试副本，违背「不粗暴终止进程」，
且与单实例机制职责重叠。旧版本实例同样持有同名互斥，新版本启动时会走「转发意图」分支。

---

## D10 托盘 HICON 换下来就销毁

**决策**：每次换图标后立即 `DestroyIcon` 上一个句柄，只在 `Dispose` 清当前句柄。

**理由**：系统在 `NIM_MODIFY` 时已复制图标，旧句柄不再被使用。
原先「只增不减、退出时统一销毁」的写法在 K02BS 阶梯推算值每轮变化时会持续累积 GDI 句柄。

---

## D11 K02BS 关机识别：接受「判不准」，写进已知限制

> **状态：已被 D13 部分推翻。** 本条的实测结论（「两态逐字节相同」）只在
> `ff=1 / ff=4` 两个端点上成立；`ff=3 / ff=5` 实际会随链路翻转，见 D13。

**决策**：不为了「关机后显示未连接」再引入新的探测手段。

**实测证据**：同一接收器在耳机开机/关机两态下，
`Render` 端点 `state=1 ff=1`、`Capture` 端点 `state=1 ff=4`，两态**逐字节相同**；
HID `0xFF90` 恒返回 `AC F8`，开关机/充电均不变。接收器完全不暴露链路状态。

**结论**：判据只能是「存在激活的 K02BS 音频端点」，接收器插着、耳机没开时仍会显示已连接。
若将来要解决，候选方向是：静音流播放测 KS 状态、USB Audio Class 时钟有效性、
或直接放弃 2.4G 判定只报「接收器在线」。**在没有新证据前不要改这段逻辑。**

## D13 K02BS 判定改为「端点分档 + 严格口径」（推翻 D11 的结论）

**新证据**（2026-10-30 22:38–22:43，同一接收器，耳机开关机反复切换，每 2 秒采样一帧）：

| 端点 | formfactor | 观测到的 DeviceState |
|---|---|---|
| 耳机（A2DP） | 3 | `0x8` ↔ `0x1` 翻转，跟随真实蓝牙链路 |
| 免提（HFP） | 5 | 同上，偶见 `0x80000008`（高位标志，低 4 位仍是 8） |
| 扬声器（2.4G） | 1 | 恒 `0x1` |
| 麦克风 | 4 | 恒 `0x1` |

追加证据：`bthprops.cpl` 的 `BLUETOOTH_DEVICE_INFO.fConnected` 与端点状态一致
（开机时 `conn=1 rem=1 auth=1`），可作为蓝牙侧的第二条独立证据。

**根因**：旧实现 `Linked = ActiveEndpoints > 0`，把 ff=1/ff=4 这两个恒激活的端点也算进去，
于是恒为 true → 卡片永远「2.4G / 双模 已连接」。README 里写的「只认 formfactor=3/5」
反而是对的，代码偏离了文档。

**决策**：
1. 蓝牙链路 = `ff=3/5` 激活 **或** HFP 已上报电量；
2. 接收器在线 = 存在任一 K02BS 端点；
3. **只有接收器在线不算已连接**（默认严格），卡片显示「未确认 · 接收器在线」，
   并沿用 10.5s 重试 / 2 次漏拍 + 90s 确认的状态机；
4. 留开关 `K02BSSoleDongleAsConnected`（默认 0）给「只用 2.4G」的用户，等价于旧行为。

**为什么不做**：不用播放静音流、不用 WASAPI 时钟、不去猜 2.4G——都没证据支持，
只会增加副作用。判定逻辑抽成纯函数 `K02BSLinkJudge`，用真值表单测，改判定先改表。

**代价**：只用 2.4G 的用户默认会看到「未确认」。这是刻意的取舍——显示「不知道」，
好过显示「已连接」但在骗人。

## D14 HFP 电量属性不能当作连接证据

**新证据**（2026-10-30 22:57，耳机已关机）：音频端点为 `ff=3/5 = 0x8`、蓝牙 API `conn=0`，
但 `FindBt("K02BS")` 仍能读到 HFP 电量 `80%`。也就是说 Windows 在断开后保留了电量属性。

**后果**：D13 的第一版仍把 `HasProperty || Level.HasValue` 当连接证据，于是关机后照样判「双模」——
用户实测复现（`BT电量=有 ; 判定=双模`）。

**决策**：
1. 蓝牙链路证据只认两条：`ff=3/5` 端点激活、`bthprops` 的 `fConnected == 1`；
2. HFP 电量只在「已确认连接」时用于显示数值，不参与连通性判断；
3. `BluetoothLink.QueryConnected()` 在 API 不可用时返回 `Unknown(-1)`，只退回端点判断，
   不当成断开（避免无蓝牙适配器的机器全判未连接）；
4. **严格口径下一律立即置为未连接**，不走 90 秒宽限：宽限是给「刚刚还在、现在读不到」的，
   而「只有接收器在线」从一开始就没有正向证据，宽限只会让 `--once` 永远显示已连接。

**验证**：耳机关机 → `--once` 输出 `CARD 西伯利亚 K02BS | mode=2.4G | connected=False | 80% |
接收器在线 · 耳机状态未确认`；开机后应回到 `双模 / connected=True`。

## D15 关机期间暂停阶梯计时

**现象**：耳机昨晚关机、今早开机后，卡片显示「已保持 11.7 小时」，主数字从 80% 掉到 76%。
这 11 小时设备根本没工作，是墙钟时间被当成了使用时间。

**决策**：蓝牙链路不通（`DongleOnly` / `None`）时调用 `PauseLadder`，恢复为 `Dual` / `Bluetooth`
时调用 `ResumeLadder`——复用「取消勾选暂停」那套机制（`PausedUtc` 记时刻，
恢复时把暂停时长补回 `BtStageUtc` / `ModeSinceUtc` / `DisconnectedSinceUtc`）。

**取舍**（用户已确认选 A）：只用 2.4G 的用户，状态长期是「未确认」，计时会一直暂停，
估算不推进。可接受——因为 2.4G 本来就没有新的阶梯上报，冻住比按墙钟下滑更接近事实。

**验证**：
- 单测：锚点 3 小时前、其中暂停 2 小时 → 恢复后只计 1 小时；重复暂停/恢复幂等。
- 端到端：人为把 `PausedUtc` 设为 2 小时前 → 跑一次 `--once`，
  「已保持」从 11.7h 变 9.8h、主数字 76%→77%、`BtStageSince` 前移 2 小时、`Paused` 复位。
